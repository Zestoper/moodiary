# 면접 예상 질문 & 답변 — Moodiary

---

## 기술 스택

**Q. 사용한 기술 스택이 뭔가요?**

백엔드는 FastAPI, 프론트엔드는 React, 스트리밍은 SSE, DB는 MySQL, 배포는 Vercel·Render·Supabase, 인증은 JWT로 했습니다.

---

## 인증

**Q. 인증은 어떻게 구현했나요?**

JWT로 구현했습니다. header에는 토큰 타입과 알고리즘(HS256)을 넣었고, payload에는 만료시간과 유저 ID를 넣었으며, signature에는 SECRET_KEY로 서명했습니다.

---

**Q. 비밀번호는 어떻게 저장했나요?**

bcrypt로 단방향 해싱 처리해서 저장했습니다.

---

**Q. 왜 bcrypt인가요?**

암호화는 양방향이라 보안에 취약합니다. bcrypt는 단방향 해시라 역산이 불가능하고, MD5나 SHA와 달리 의도적으로 느리게 설계되어 무차별 대입 공격에 강합니다.

---

**Q. 로그인 시 비밀번호 비교는 어떻게 하나요?**

`verify_password()`로 비교했습니다. bcrypt가 입력한 평문을 다시 해시해서 저장된 해시값과 비교하는 방식입니다.

---

**Q. JWT가 탈취되면 어떻게 되나요?**

만료시간 전까지 누구든 그 토큰으로 API 요청할 수 있습니다. 완벽한 방어는 없지만, 만료시간을 60분으로 짧게 설정하고 로그아웃 시 localStorage에서 즉시 삭제하는 방식으로 피해를 최소화했습니다.

---

**Q. 로그인 만료 처리는 어떻게 했나요?**

토큰 만료시간은 7일로 설정했고, 만료 시 axios 인터셉터가 401 응답을 감지해서 localStorage에서 토큰을 삭제하고 로그인 페이지로 이동하게 했습니다.

---

## SSE 스트리밍

**Q. SSE 스트리밍은 어떻게 구현했나요?**

백엔드에서 AI 응답을 `yield`로 청크 단위로 보내고 `StreamingResponse`로 반환했습니다. 프론트에서는 `fetch`의 `ReadableStream`으로 청크가 올 때마다 읽어서 AI 말풍선에 이어붙였습니다.

---

**Q. axios 대신 fetch를 쓴 이유는?**

axios는 응답을 다 받은 후 처리해서 스트리밍이 불가능합니다. fetch의 ReadableStream은 청크가 올 때마다 즉시 처리할 수 있어서 사용했습니다.

---

**Q. 왜 SSE를 썼나요?**

AI 응답을 다 생성할 때까지 기다렸다가 한 번에 보내면 로딩 화면만 보여 UX가 좋지 않습니다. SSE를 쓰면 청크 단위로 실시간으로 보여줄 수 있어서 ChatGPT처럼 타이핑 효과를 줄 수 있습니다.

---

**Q. WebSocket 대신 SSE를 쓴 이유는?**

AI 채팅은 유저가 보내고 서버가 응답하는 단방향 구조라 SSE로 충분했습니다. WebSocket은 양방향 동시 송수신이 필요할 때 쓰는 게 더 적합합니다.

---

## DB 설계

**Q. DB 설계에서 신경 쓴 부분이 있나요?**

CASCADE와 SET NULL을 고민했습니다. 유저 삭제 시 일기는 의미가 없어서 CASCADE로 같이 삭제했고, 일기 삭제 시 채팅 기록은 대화 내용을 보존해야 해서 SET NULL로 처리했습니다. 또한 중복 결제 방지를 위해 `payments.imp_uid`에 UNIQUE 제약을 걸었습니다.

---

## 크레딧 시스템

**Q. 크레딧 시스템은 어떻게 구현했나요?**

기능별 월간 사용 횟수를 `usage_quotas` 테이블에 기록했습니다. 맞춤 솔루션 월 3회, 연애 상담 월 5회, 월간 리포트 월 1회로 제한했고, 무료 한도 초과 시 크레딧 1개 차감, 크레딧도 없으면 402 에러와 함께 결제 페이지로 이동하게 했습니다.

---

## 보안

**Q. 보안은 어떻게 신경 썼나요?**

비밀번호는 bcrypt로 해시해서 저장했고, JWT 인증으로 모든 API를 보호했습니다. SECRET_KEY 같은 민감한 정보는 환경변수로 관리해서 Git에 올라가지 않게 했습니다. 또한 PDF 내보내기 시 사용자 입력값을 `escapeHtml()`로 처리해서 XSS 공격을 방지했습니다.

---

**Q. XSS가 뭔가요?**

사용자 입력에 악성 스크립트를 넣어서 실행시키는 공격입니다. 일기 내용에 `<script>` 태그를 넣고 PDF HTML에 그대로 삽입되면 브라우저가 실행합니다. `escapeHtml()`로 `<`, `>` 같은 태그를 문자열로 변환해서 방지했습니다.

---

## 상태관리

**Q. React에서 상태관리는 어떻게 했나요?**

컴포넌트 내부 상태는 `useState`로 관리했고, 전역 상태는 Context API로 관리했습니다. 로그인 유저 정보와 토큰은 `AuthContext`에서 `useAuth()`로 어느 페이지에서든 접근할 수 있게 했고, 알림 메시지는 `ToastContext`로 `addToast()`를 전역에서 호출할 수 있게 했습니다.

---

**Q. Redux는 왜 안 썼나요?**

프로젝트 규모가 크지 않아서 Context API로 충분했습니다. Redux는 상태가 복잡하고 많을 때 유용한데, 이 프로젝트는 전역으로 관리할 상태가 유저 정보와 토스트 알림뿐이라 Context API가 더 적합했습니다.

---

**Q. axios 인터셉터를 왜 사용했나요?**

API가 많아지면 모든 요청에 JWT 토큰을 수동으로 붙여야 합니다. 인터셉터를 쓰면 한 곳에서 한 번만 처리할 수 있어서 유지보수가 편합니다. 또한 401 응답 시 토큰 삭제와 로그인 페이지 이동도 인터셉터에서 일괄 처리했습니다.

---

**Q. localStorage를 사용할 때 주의할 점은 뭔가요?**

localStorage는 JS로 접근 가능해서 XSS 공격 시 토큰이 탈취될 수 있습니다. HttpOnly Cookie를 쓰면 JS 접근이 불가능해서 더 안전하지만, 이 프로젝트는 포트폴리오용이라 localStorage를 사용했습니다.

---

## 컴포넌트 구조

**Q. React에서 컴포넌트를 어떻게 나눴나요?**

페이지 단위는 `pages/`에, 여러 페이지에서 재사용하는 컴포넌트는 `components/`에 분리했습니다. 예를 들어 하단 네비게이션 바는 모든 페이지에서 공통으로 쓰여서 `BottomNav` 컴포넌트로 분리했습니다.

---

**Q. useEffect를 어디서 어떻게 활용했나요?**

마운트 시 데이터 로딩에 `useEffect(fn, [])`를 사용했고, ChatPage에서 메시지가 올 때마다 자동 스크롤되게 `useEffect(fn, [messages])`를 사용했습니다. 또한 DiaryPage에서 타이핑이 500ms 멈추면 localStorage에 초안을 자동저장하는 debounce도 `useEffect`로 구현했습니다.

---

**Q. debounce가 뭔가요?**

타이핑할 때마다 localStorage에 저장하면 성능 낭비라서, 멈춘 후 500ms 후에만 저장하는 기법입니다.

---

## 배포

**Q. 프로젝트 배포는 어떻게 했나요?**

백엔드는 Render, 프론트엔드는 Vercel, DB는 Supabase로 배포했습니다.

---

**Q. Supabase를 쓴 이유가 뭔가요?**

Render에서 MySQL 무료 플랜이 없어서 PostgreSQL을 무료로 제공하는 Supabase를 사용했습니다.

---

## 마무리

**Q. 가장 어려웠던 점이 뭔가요?**

DB 설계가 어려웠습니다. 테이블 간 1:N 관계와 CASCADE, SET NULL 중 어떤 걸 써야 할지 고민했습니다. 유저 삭제 시 일기는 의미가 없어서 CASCADE로 같이 삭제하고, 일기 삭제 시 채팅 기록은 SET NULL로 보존하는 방식으로 해결했습니다.

---

**Q. 이 프로젝트를 통해 배운 점이 뭔가요?**

JWT 인증 흐름을 정확하게 이해했고, SSE 스트리밍을 직접 구현하면서 axios와 fetch의 차이, 백엔드에서 `yield`로 데이터를 흘려보내는 방식을 배웠습니다. 또한 DB 설계에서 테이블 간 관계와 CASCADE, SET NULL 같은 제약 조건을 직접 고민하면서 데이터 무결성의 중요성을 배웠습니다.
