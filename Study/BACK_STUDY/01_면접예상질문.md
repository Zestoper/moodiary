## JWT 인증

**Q. JWT 토큰이 뭔가요? 이 프로젝트에서 어떻게 사용했나요?**

JWT(JSON Web Token)는 `header.payload.signature` 세 부분으로 이루어진 문자열입니다.
로그인 성공 시 서버가 발급하고, 이후 모든 요청 헤더에 `Authorization: Bearer <토큰>` 형태로 첨부해 인증합니다.

이 프로젝트에서는 `core/security.py`의 `create_access_token()`으로 발급하고, `decode_access_token()`으로 검증합니다.
`auth.py`의 `get_current_user()` 함수가 FastAPI `Depends()`로 모든 인증이 필요한 엔드포인트에 주입됩니다.

---

**Q. JWT는 왜 안전한가요? 위조가 불가능한 이유는요?**

payload는 누구나 디코딩할 수 있지만, signature가 `SECRET_KEY + 알고리즘(HS256)`으로 서명되어 있어 키를 모르면 변조할 수 없습니다.
서버에서 `jwt.decode()` 시 signature를 검증하기 때문에, 내용을 조작하면 즉시 `JWTError`가 발생합니다.

---

**Q. 토큰 만료는 어떻게 처리하나요?**

`create_access_token()`에서 payload에 `exp` 필드를 추가합니다.
`jwt.decode()` 호출 시 `python-jose`가 자동으로 만료 여부를 확인하고, 만료됐으면 `JWTError`를 던집니다.
이 프로젝트는 Refresh Token 없이 Access Token만 사용 중이며, 만료 시 프론트 axios 인터셉터가 로그인 페이지로 리다이렉트합니다.

## FastAPI

**Q. FastAPI의 `Depends()`가 뭔가요?**

의존성 주입(Dependency Injection) 메커니즘입니다.
`db: Session = Depends(get_db)` 처럼 선언하면 FastAPI가 라우터 함수 실행 전에 `get_db()`를 자동 호출해서 세션을 넘겨줍니다.
`get_current_user()` 같은 인증 로직도 같은 방식으로 모든 보호 엔드포인트에 재사용됩니다.

---

**Q. `get_db()` 함수에서 `yield`를 쓰는 이유가 뭔가요?**

`yield`를 쓰면 제너레이터 함수가 됩니다.
`yield db`에서 DB 세션을 라우터에 넘겨주고, 라우터 실행이 끝나면 `finally: db.close()`가 항상 실행되어 커넥션을 반환합니다.
예외가 발생해도 `finally`는 반드시 실행되므로, 커넥션 누수를 방지할 수 있습니다.

---

**Q. Pydantic 스키마와 SQLAlchemy 모델의 차이점은 무엇인가요?**

- **SQLAlchemy 모델** (`models/user.py`): DB 테이블과 매핑되는 ORM 클래스. 실제 DB 컬럼을 정의합니다.
- **Pydantic 스키마** (`schemas/user.py`): API의 요청/응답 데이터 형태를 정의. 유효성 검사(min_length, EmailStr 등)를 자동 처리합니다.

두 개를 분리하는 이유는, DB 모델(`User`)을 그대로 반환하면 `hashed_password` 같은 민감한 필드까지 JSON에 포함될 수 있기 때문입니다. `response_model=UserResponse`를 지정하면 FastAPI는 `UserResponse`에 정의된 필드만 JSON으로 변환하므로, `hashed_password`는 처음부터 응답에 포함되지 않습니다.

---

**Q. FastAPI에서 422 에러는 언제 발생하나요?**

요청 바디가 Pydantic 스키마 검증을 통과하지 못할 때 FastAPI가 자동으로 반환합니다.
예: `UserRegister`에서 `password: str = Field(min_length=6)`인데 5자 이하 비밀번호를 보내면 422가 납니다.
이때 `detail`은 문자열이 아닌 배열(`[{msg, loc, type}]`)이므로, 프론트에서 별도 파싱이 필요합니다.

## SQLAlchemy / DB

**Q. `db.commit()` 전에 `db.add()`만 하면 어떻게 되나요?**

`db.add()`는 세션 메모리에 변경사항을 올려놓을 뿐, DB에 실제로 반영되지 않습니다.
`db.commit()` 호출 시 비로소 INSERT/UPDATE/DELETE 쿼리가 실행됩니다.
`autocommit=False` 설정 덕분에 여러 작업을 하나의 트랜잭션으로 묶을 수 있습니다.

---

**Q. `db.refresh(obj)`는 왜 호출하나요?**

`db.commit()` 이후에도 파이썬 객체에는 DB가 자동 생성한 값(예: `id`, `created_at`)이 반영되지 않습니다.
`db.refresh()`를 호출하면 DB에서 최신 값을 다시 읽어와 객체를 갱신합니다.

---

**Q. 이 프로젝트에서 `usage_quotas` 테이블의 유니크 제약은 왜 필요한가요?**

`(user_id, feature, year, month)` 복합 유니크 제약이 없으면 같은 유저의 같은 기능·같은 달 레코드가 중복 생성될 수 있습니다.
중복 INSERT 대신 기존 레코드의 `count`를 증가시켜야 하기 때문에, 이 제약으로 레코드가 하나뿐임을 보장합니다.

## SSE 스트리밍

**Q. SSE가 뭔가요? WebSocket과 차이는요?**

SSE(Server-Sent Events)는 서버 → 클라이언트 단방향 실시간 데이터 전송 방식입니다.
WebSocket은 양방향이지만, AI 응답처럼 서버만 보내는 경우엔 SSE가 더 단순하고 HTTP 표준을 그대로 사용합니다.

이 프로젝트의 `/api/chat/stream`은 FastAPI `StreamingResponse`와 파이썬 제너레이터로 구현되어 있습니다.

---

**Q. `/api/chat/stream`에서 스트리밍이 끝난 후 DB 저장을 새 세션으로 하는 이유가 뭔가요?**

제너레이터 함수(`generate()`)는 `StreamingResponse`가 비동기로 실행합니다.
기존 `db` 세션은 라우터 함수 스코프에서 만들어졌고, 제너레이터 안에서 쓰면 이미 닫힌 세션일 수 있습니다.
그래서 스트리밍 완료 후 `new_db = SessionLocal()`로 별도 세션을 열어 AI 메시지를 저장하고, `finally: new_db.close()`로 닫습니다.

## 보안 / 배포

**Q. `allow_origins=["*"]`의 보안 위험은 무엇인가요?**

모든 출처에서 API를 호출할 수 있게 되어 CSRF 공격에 취약해집니다.
운영 환경에서는 `allow_origins=["https://moodiary.vercel.app"]`처럼 프론트 도메인만 허용해야 합니다.
이 프로젝트는 포트폴리오 목적으로 `*`를 사용 중입니다.

---

**Q. 비밀번호를 bcrypt로 해시하는 이유가 뭔가요?**

bcrypt는 단방향 해시로 역산이 불가능합니다.
같은 비밀번호라도 매번 다른 해시가 생성됩니다(salt). DB가 유출되어도 원본 비밀번호를 알 수 없습니다.
MD5나 SHA는 빠르기 때문에 레인보우 테이블 공격에 취약하지만, bcrypt는 의도적으로 느리게 설계되어 있습니다.

---

**Q. Render 배포 시 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`를 startup에서 하는 이유는요?**

Alembic 마이그레이션을 별도로 실행하지 않은 상태로 배포할 때, 기존 DB에 새 컬럼(`is_admin`, `credits`)이 없어 런타임 오류가 발생합니다.
`IF NOT EXISTS` 구문을 사용해 컬럼이 이미 있으면 스킵하므로 중복 실행해도 안전합니다.

## AI 연동

**Q. Groq API에서 모델을 두 개(LLaMA / Qwen3) 쓰는 이유가 뭔가요?**

- **LLaMA 3.3 70B**: 감정 분석·솔루션·리포트·상담처럼 정확한 JSON 응답이 필요한 작업에 사용합니다.
- **Qwen3-32B**: 채팅 스트리밍에 사용합니다. 한국어 맞춤법·띄어쓰기가 LLaMA보다 정확하고, `/no_think` 플래그로 Chain-of-Thought를 끄면 빠른 응답이 가능합니다.

---

**Q. `temperature` 값을 감정 분석은 0.3, 채팅은 0.7로 다르게 설정한 이유는요?**

- `0.3` (낮을수록 일관적): 감정 분석은 매번 같은 형식의 JSON을 내야 하므로 창의성보다 일관성이 중요합니다.
- `0.7` (높을수록 창의적): 채팅은 자연스럽고 다양한 답변이 필요하므로 약간의 창의성이 필요합니다.
