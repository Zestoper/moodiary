## 1. HTTP 메서드 의미

| 메서드 | 의미 | 이 프로젝트 예시 |
|---|---|---|
| GET | 데이터 조회 | `GET /api/diary` — 일기 목록 |
| POST | 새 데이터 생성 | `POST /api/diary` — 일기 작성 |
| PUT | 전체 수정 | `PUT /api/diary/{id}` — 일기 수정 |
| PATCH | 부분 수정 | `PATCH /api/auth/me` — 닉네임만 수정 |
| DELETE | 삭제 | `DELETE /api/diary/{id}` — 일기 삭제 |

## 2. HTTP 상태 코드

| 코드 | 의미 | 이 프로젝트에서 쓰이는 상황 |
|---|---|---|
| 200 | OK | 일반 조회/수정 성공 |
| 201 | Created | 일기/회원가입/상담 생성 성공 |
| 204 | No Content | 삭제 성공 (응답 바디 없음) |
| 400 | Bad Request | 이메일 중복, 잘못된 패키지 ID |
| 401 | Unauthorized | 토큰 없음/만료/위조 |
| 402 | Payment Required | 쿼터 초과 + 크레딧 없음 |
| 403 | Forbidden | 관리자 아닌데 `/admin` 접근 |
| 404 | Not Found | 없는 일기/유저 조회 |
| 409 | Conflict | 이미 처리된 결제(imp_uid 중복) |
| 422 | Unprocessable Entity | Pydantic 유효성 검사 실패 |
| 500 | Internal Server Error | 서버 내부 오류 |

## 3. JWT 구조와 흐름

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIiwiZXhwIjoxNzE2MDAwMDAwfQ.서명
      ↑ header           ↑ payload                               ↑ signature
```

**흐름**
1. 로그인 → 서버가 `SECRET_KEY`로 서명한 JWT 발급
2. 프론트는 `localStorage`에 토큰 저장
3. 이후 모든 요청 헤더: `Authorization: Bearer <토큰>`
4. 서버는 `decode_access_token()`으로 유저 ID 추출

**중요**: payload는 base64 인코딩이라 누구나 디코딩 가능합니다. 민감한 정보(비밀번호 등)는 절대 넣지 않습니다.

## 4. bcrypt 단방향 해시

```
"1234" → bcrypt → "$2b$12$eImiTXuWVxfM37uY4JANjQ..."
```

- **단방향**: 해시 → 원본 복원 불가능
- **salt 자동 생성**: 같은 "1234"도 실행마다 다른 해시 → 레인보우 테이블 공격 방어
- `verify_password("1234", "$2b$12$...")` → 내부적으로 재해시 후 비교

SHA256, MD5는 빠르기 때문에 무차별 대입 공격에 취약합니다. bcrypt는 의도적으로 느립니다.

## 5. CORS (Cross-Origin Resource Sharing)

프론트(`http://localhost:3000`)가 백엔드(`http://localhost:8000`)에 요청할 때, 브라우저가 보안상 막는 정책이 CORS입니다.

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],   # 현재: 모든 출처 허용
    allow_credentials=False,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

- `allow_origins=["*"]` — 개발/포트폴리오용. 운영에선 `["https://moodiary.vercel.app"]`로 제한해야 합니다.
- `allow_credentials=True`이면 쿠키/인증 정보도 허용하나, `allow_origins=["*"]`와 함께 사용 불가합니다.

## 6. ORM (Object-Relational Mapping)

SQL을 직접 쓰는 대신 파이썬 객체로 DB를 다루는 방식입니다.

```python
# SQL 직접
SELECT * FROM diaries WHERE user_id = 1 ORDER BY created_at DESC;

# ORM (SQLAlchemy)
db.query(Diary).filter(Diary.user_id == 1).order_by(Diary.created_at.desc()).all()
```

**장점**: SQL 인젝션 방어, 파이썬 코드로 DB 조작, DB 종류 변경 시 코드 수정 최소화

## 7. 트랜잭션 (Transaction)

여러 DB 작업을 하나의 단위로 묶는 것입니다.

```python
user_msg = ChatMessage(role="user", ...)
ai_msg   = ChatMessage(role="assistant", ...)
db.add(user_msg)
db.add(ai_msg)
db.commit()  # 두 개가 동시에 저장됨. 하나라도 실패하면 둘 다 롤백
```

`autocommit=False` 덕분에 `db.commit()` 전까지 변경사항이 DB에 반영되지 않습니다.

## 8. 인덱스 (Index)

```python
user_id = Column(Integer, nullable=False, index=True)
```

- `index=True` — 해당 컬럼에 DB 인덱스를 생성합니다.
- 인덱스 없이 필터링: 테이블 전체를 순회 (Full Table Scan)
- 인덱스 있으면: B-Tree로 빠르게 검색 (O(log n))

`user_id`로 자주 조회하는 테이블(diaries, chat_messages, usage_quotas)에 모두 index를 걸어두었습니다.

## 9. UNIQUE 제약 (Unique Constraint)

```python
# 단일 컬럼 유니크
imp_uid = Column(String(100), unique=True)

# 복합 유니크
__table_args__ = (
    UniqueConstraint('user_id', 'feature', 'year', 'month'),
)
```

- 중복 INSERT 시 DB가 `IntegrityError`를 발생시킵니다.
- `payments.imp_uid`: 같은 결제가 두 번 처리되는 것을 막습니다.
- `usage_quotas`: 같은 유저·기능·월 레코드가 하나만 존재하도록 보장합니다.

## 10. REST API 설계 원칙

```
GET    /api/diary         → 목록 조회
POST   /api/diary         → 생성
GET    /api/diary/{id}    → 단건 조회
PUT    /api/diary/{id}    → 수정
DELETE /api/diary/{id}    → 삭제
POST   /api/diary/{id}/solution → 특수 동작 (하위 리소스)
```

- URL은 **명사**(diary), 동작은 **HTTP 메서드**로 표현합니다.
- `/getDiaries`, `/createDiary` 같은 동사형 URL은 REST 원칙에 어긋납니다.
- 계층 관계는 `/api/diary/{id}/solution` 처럼 표현합니다.

## 12. 의존성 주입 (Dependency Injection) 원칙

```python
# 나쁜 예 — 함수 내부에서 직접 생성
def get_diaries():
    db = SessionLocal()  # 테스트 불가, 커넥션 누수 위험
    ...

# 좋은 예 — 외부에서 주입
def get_diaries(db: Session = Depends(get_db)):
    ...  # db는 FastAPI가 관리, 테스트 시 mock 가능
```

- 의존하는 객체를 직접 생성하지 않고, 외부에서 주입받습니다.
- 테스트할 때 실제 DB 대신 가짜(mock) DB 세션을 주입할 수 있습니다.
- FastAPI의 `Depends()`가 이 패턴을 프레임워크 수준에서 지원합니다.
